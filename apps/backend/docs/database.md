# Database

The backend uses PostgreSQL with SQLAlchemy's asynchronous APIs. Database schema
changes are managed with Alembic.

## Defining models

All SQLAlchemy models must inherit from `app.database.base.Base`. The base provides
the naming convention used for indexes and database constraints.

Use SQLAlchemy 2 typed mappings:

```python
from sqlalchemy.orm import Mapped, mapped_column

from app.database.base import Base


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
```

Place feature-specific models in their feature module, for example:

```text
app/modules/users/models.py
```

## Registering models

Every model module must be imported by `app/database/models.py`:

```python
from app.modules.users.models import User

__all__ = ["User"]
```

Alembic imports `app.database.models` before reading `Base.metadata`. A model that is
not registered there will not be detected by:

```console
uv run alembic revision --autogenerate
```

Keep model implementations in their feature modules. Use `app/database/models.py`
only as the central model registry.

## Engine and sessions

The database engine and session factory are created during the FastAPI
application lifespan and stored in `app.state`. Application code must access
them through the dependencies defined in `app/api/deps.py`:

* `DatabaseDep` provides the database engine and session factory.
* `SessionDep` provides an `AsyncSession` scoped to the request dependency.

Do not create engines or session factories at module import time. Use
SQLAlchemy's asynchronous APIs for database I/O.

The current `SessionDep` manages session lifetime but does not commit
transactions automatically. Code that writes data must define its transaction
boundary explicitly. Do not add an implicit commit to the shared dependency
without first establishing a project-wide transaction convention.

## Configuration

The backend reads the following client settings:

| Variable | Default | Description |
| --- | --- | --- |
| `BACKEND_DATABASE_URL` | empty | Complete SQLAlchemy connection URL; overrides the individual connection fields |
| `BACKEND_POSTGRES_HOST` | `localhost` | PostgreSQL server hostname |
| `BACKEND_POSTGRES_PORT` | `5432` | PostgreSQL server port |
| `BACKEND_POSTGRES_USER` | `web_app_runtime` | PostgreSQL username |
| `BACKEND_POSTGRES_PASSWORD` | `changepassword` | PostgreSQL password |
| `BACKEND_POSTGRES_DB` | `web_app` | PostgreSQL database name |
| `BACKEND_DB_POOL_SIZE` | `5` | Regular connections per application worker |
| `BACKEND_DB_MAX_OVERFLOW` | `5` | Extra connections per worker during traffic bursts |
| `BACKEND_DB_POOL_TIMEOUT` | `30` | Seconds to wait when all connections are busy |
| `BACKEND_DB_POOL_RECYCLE` | `1800` | Replace connections older than this many seconds |
| `BACKEND_DB_POOL_PRE_PING` | `true` | Check a connection before using it |

Use `BACKEND_DATABASE_URL` for managed Postgres or TLS settings:

```env
BACKEND_DATABASE_URL=postgresql+psycopg://user:password@db.example.com:5432/web_app?sslmode=require
```

When `BACKEND_DATABASE_URL` is set, the individual `BACKEND_POSTGRES_*`
fields are ignored. The legacy `POSTGRES_*` names and
`POSTGRES_RUNTIME_PASSWORD` remain accepted as fallbacks.

## Connection capacity

Each application worker has its own connection pool. `BACKEND_DB_POOL_SIZE`
sets its regular size. `BACKEND_DB_MAX_OVERFLOW` allows extra connections during
traffic bursts. These extra connections are closed after use.

Calculate the maximum number of application connections as:

```text
replicas * workers * (DB_POOL_SIZE + DB_MAX_OVERFLOW)
```

For example, one backend replica with four workers and the default settings can
open up to 40 PostgreSQL connections.

Keep this number below PostgreSQL `max_connections`. Leave some connections for
migrations, monitoring, administrative access, and other database clients. The
migration process opens one temporary connection.

When all connections are busy, a request waits for up to
`BACKEND_DB_POOL_TIMEOUT` seconds and then fails with a pool timeout.

## Creating migrations

With PostgreSQL available, generate a migration from `apps/backend/`:

```console
uv run --env-file ../../.env alembic revision --autogenerate -m "describe the change"
```

The post-write hooks in `alembic.ini` apply Ruff fixes and formatting to newly
generated revisions.

Always review an autogenerated migration before applying it. Verify:

* table and column names;
* nullability and server defaults;
* indexes and unique constraints;
* foreign keys and deletion behavior;
* `upgrade()` and `downgrade()` operations;
* unexpected table or column removal.

Do not modify a migration that has already been shared or applied. Create a new
revision instead.

## Applying migrations

Show the currently applied revision:

```console
uv run --env-file ../../.env alembic current
```

Show migration history:

```console
uv run --env-file ../../.env alembic history
```

Apply all pending migrations:

```console
uv run --env-file ../../.env alembic upgrade head
```

Roll back the latest migration in a local development environment:

```console
uv run --env-file ../../.env alembic downgrade -1
```

If the required database environment variables are already exported in the
current shell, `--env-file ../../.env` can be omitted.

## Testing database behavior

Use the `unit` marker for isolated service tests where the engine or session is
mocked. Tests that exercise actual database integration must use the
`integration` marker and run against an isolated development or test database.

Run unit tests:

```console
uv run pytest -m unit
```

With the required external services available, run integration tests from
`apps/backend/`:

```console
uv run --env-file ../../.env pytest -m integration
```
